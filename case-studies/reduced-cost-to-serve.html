Why This Problem Mattered?

Situation

Funding winter led to customers renegotiating subscriptions, churn, and revenue drop.

Triggered a hiring freeze. Increased work pressure lowered employee NPS.

Company decided to chase Enterprise customer aggressively in US and EU markets.

Revised product OKRs focused on lower cost to serve and faster revenue recognition.

Complication

Onboarding was slow and heavily dependent on IMs (internal team members), delaying billing.

Tech + design debt in the Settings module was a key blocker to reducing cost to serve and lowering manual support burden.

Throwing people at the problem was no longer viable due to hiring freeze.

Strategic Response

Prioritized SMS module in Settings module as the revamp starting point.

SMS module scored high in complexity and design pattern reusability, with 60-80% reused in multiple modules.

Building on its success, we aimed to extend its UX for WhatsApp, Email, and RCS modules in Settings.

Discovery to Clarity: Understanding the Problem Space

Collected information on current state

  1. Context of use queries
    1. Consulted PMs and IMs
    2. Inquired what triggers user to use it, what they do while performing task and what they do post that?
  2. Age of current design
    1. 90% of the design patterns and functionalities are 4-5 years old.
    2. Several old design files and PRD were not found.
  3. Use-case information
    1. Info around use-cases / features was scattered all over the place.
    2. Some team members had left, so consulted cross-functional stakeholders to gather all possible info.
  4. Data tracking reliability
    1. Data is tracked in Amplitude, but is not tracked as efficiently on the ones built in the last 3 years.
    2. However, LogRocket, a heatmap tool, could be used to extract useful insights.

Framed a conceptual model to convey my understanding of the SMS config module

Drew a functionality tree outlining the module's structure, scale, and variance, then consulted stakeholders to confirm if my understanding is on the right track.

Led a scenario mapping workshop to uncover details at each step of the user journey

  1. Information was scattered across teams, docs etc, so gathered key stakeholders to answer ambiguities and unknowns.
  2. Conducted a scenario mapping workshop with stakeholders from product, engineering, and the IM team.
  3. Discussed info related to happy path, unhappy path, and alternate paths.
  4. Sought clarity on data and context of use.

Conducted qualitative study through stakeholder interviews

  1. Participants
    1. SVP of Product
    2. Implementation Managers
    3. Engineers (FE, BE, QA)
  2. Key Insights
    1. High frequency of use during the onboarding phase. Later goes down.
    2. The user could be a Marketer / Developer / IM.
    3. Businesses use 1 or 2 connectors only.
    4. Making all connectors always visible is not a critical business need.
    5. Struggle to identify default sender.

Conducted quantitative study through data analysis

  1. Collaborators
    1. Product Analyst
    2. FE
  2. Key Insights
    1. 90% businesses use 1 connector.
    2. 9% businesses use 2 connectors.
    3. Frequency of visit decreases substantially after sending 1-2 campaigns successfully.
    4. Median length of Sender Name is 16.5 and max length is 38.
    5. Median length of Customer Service Provider is 15 and max length is 16.

Analyzed User Interactions

Exploratory question for analyzing heatmaps

What do click distribution, hover patterns, scroll depth, dead clicks, and rage clicks reveal about user behavior?

Key learning areas

  1. Which areas of a page are getting the most attention or clicks?
  2. Are users finding and using the primary calls to action?
  3. Do any non-clickable elements receive a lot of clicks, indicating possible user confusion?
  4. Which parts of the layout are effectively drawing user interest, and which are not?
  5. How far down do most users scroll on a page?
  6. Are key messages or calls to action placed in areas where users are most likely to see them?
  7. Are there areas of the page where users hover frequently, possibly indicating reading or indecision?

Turned overwhelm into clarity through Context-aware design

Before

Context-blind UX

New and repeat user see the same nested tab layout and editable form upon landing.

After

Context-aware UX

UI behavior shifts OR flows and feature surface based on user stage, role, and permissions.

For example, the landing page adapts based on user stage (new vs. repeat).

User stageRolesPermission

Before: Non-adaptive UX. New and repeat user see the same nested tab layout and editable form upon landing. After: Context-aware UX. UI behavior shifts OR flows and feature surface based on user stage, role, and permissions. For example, landing page adapts based on user stage (new vs. repeat). Venn: User stage, Roles, Permissions.

New User → Given a clear starting point. i.e. Select a service provider

Repeat User → Listed configured senders only

UI adapts to user roles, permissions, and connector-specific features

Only one sender can be marked as default. The default one always appears at the top.

Connectors may have unique features like the Re-authentication CTA in Twilio. The second field in the card may vary across connectors.

The More menu is hidden for users without edit permissions.

If a user is never permitted to perform an action, the option won't appear in the menu.

If an action requires admin approval, it will appear disabled with a tooltip guiding the next step.

Revealed user struggles. Justified retiring the flow.

Hitting Save CTA ≠ Work done

Users expected Save to finish the task. It didn’t, and that surprised them.

A hidden surprise step caused task abandonment

  • What changed: After Save, an extra form appeared below the fold.
  • Why it failed: No auto-scroll, so many users missed the next step.
  • How we know: Heatmaps showed users skimming past the text and treating reading as a chore.

Heatmap shown in two parts. The tool can’t capture full screens yet.

That friction cost us support time

Open settings
Go to SMS
Choose connector
Add sender
Fills sender form
Clicks Save(user assumes task is done)
Screen reloads with an unexpected additional form
Save CTA(final save, but confidence is shaken)

Friction

User sees no cue indicating that an additional form has to be filled after clicking SAVE.

Resulted in

  • Increased CS tickets
  • Increased IM sync-ups
  • Increased CSM sync-ups

Team agreed to retire legacy flow

The layout and structure weren’t serving users or business goals.
Got buy-in to reimagine both from the ground up.
